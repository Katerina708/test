# Тестовое задание

Скрипт читает выгрузку заказов `sales.csv` и формирует файл
`daily_by_sku.csv` со строками «артикул — день» и колонками
`sku, order_date, orders, revenue`.

## Требования

- Python 3.9+ (используется только стандартная библиотека, внешних
  зависимостей нет).

## Запуск

1. Положить `report.py` и `sales.csv` в одну папку.
2. Открыть терминал (Windows: `Win + R` → `cmd`; macOS/Linux:
   Terminal) и перейти в эту папку. Например:

   cd C:\Users\имя\путь\к\папке
3. Затем выполнить:
   python report.py
4. Рядом в папке появится  daily_by_sku.csv. В консоль печатается краткий отчёт: сколько строк прочитано, сколько уникальных заказов учтено.

## Результат
Результат на исходном sales.csv: обработано 13 794 уникальных
заказа, на выходе 630 строк (пар «артикул × день»).

## Как обрабатывались данные
orders — число уникальных order_id по артикулу за день, включая
отменённые заказы.

revenue — сумма quantity × price только по статусу delivered.

Один заказ (order_id + sku + дата) учитывается один раз, даже если строка встретилась в выгрузке дважды.

Строки отсортированы по sku, затем по order_date.

## Проблемы в данных и как они обработаны
Разный регистр и написание статуса. Встречаются все варианты:
delivered, Delivered, DELIVERED, cancelled, Cancelled,
CANCELLED, а также canceled с одной l. Привожу к нижнему
регистру через strip().lower() и сверяю со словарём допустимых статусов.
Неизвестные статусы — отбрасываю.

Дубли строк — 60 штук. Шестьдесят строк полностью повторяют
уже встречавшуюся комбинацию order_id + sku + order_date.
Удаляю повторы по этому ключу, оставляя первое вхождение.

Пустой quantity — 4 строки. В них заполнены price и
status, но нет количества. Отбрасываю: без
количества нельзя посчитать revenue, а в orders такая
строка тоже бесполезна.

Лишние пробелы в конце строк. Часть строк оканчивается
пробелом после статуса. Обрабатываю через .strip() для всех
строковых полей.

Чистые данные (проверила, ничего делать не пришлось):

все даты в формате ГГГГ-ММ-ДД, «кривых» нет;

quantity — целое 1/2/3 (кроме 4 пустых строк выше);

price — целый положительный;

12 уникальных SKU (UYT-0001…UYT-0012), у каждого своя
постоянная цена;

диапазон дат: 2026-08-17 — 2026-10-11 (56 дней).

## Как проверяла расчёт
Собственный скрипт для анализа исходных данных. Отдельно
написала analyze.py, который независимо от report.py
считает по sales.csv: общее число строк, разбивку по
написаниям статуса, число строк с пустым quantity, число
дублей по ключу order_id + sku + order_date, диапазон дат и
сумму quantity × price по delivered. Цифры из этого скрипта
использовала для сверки.

Сходимость уникальных заказов. В исходнике 13 798 разных
order_id. После отбрасывания 4 строк с пустым quantity
остаётся 13 794 — ровно столько, сколько вывел скрипт. Значит,
чистка не «теряет» заказы без причины.

Сверка общей выручки. Сумма quantity × price по
delivered в исходном файле (с дублями) — 10 319 900 ₽. После
удаления 60 дублей в daily_by_sku.csv сумма revenue —
10 276 540 ₽. Разница — 43 360 ₽ — ровно стоимость
продублированных delivered-заказов, что подтверждает
корректность дедупликации.

Сходимость цены. Для нескольких SKU убедилась, что все
значения revenue в daily_by_sku.csv делятся на цену этого
SKU без остатка — значит, выручка считается по правильной цене,
а не по «средней по больнице».

## Ограничения и что не доделано
Один и тот же order_id с разными статусами (delivered и
cancelled) — беру первое вхождение. Если в реальной выгрузке
такие конфликты есть, их стоило бы обрабатывать по времени
обновления, но такого поля в исходных данных нет.

Дробное quantity отбрасывается как ошибка ввода. Для мерных
товаров (кг, метры) логика была бы другой — здесь считаю, что
товары штучные.

sku сравнивается как строка с учётом регистра. Если бы в
выгрузке встретились uyt-0231 и UYT-0231 как один товар,
это не нормализуется, нужна отдельная договорённость.

Не учтены все вариации ошибочного написания статусов.
